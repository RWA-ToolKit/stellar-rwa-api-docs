# API Overview

<LastReviewed date={metadata.lastReviewed} />

The Stellar RWA API is a **read-only** REST service that indexes all tokenized
asset activity on Stellar and serves it as JSON. It is written in Rust (Axum +
tokio) and holds no keys — it never signs or submits transactions.

**Base URL:** Set via environment variable `NEXT_PUBLIC_API_BASE_URL` (defaults to `http://localhost:8080` for development). Readers should replace examples with their configured URL.

<CalloutBox variant="tip">
An OpenAPI 3.0 specification is available at <code>/openapi.json</code> — use it with Swagger UI, Postman, or to generate SDK clients. See <a href="/docs/integration">Integration Guide</a> for examples.
</CalloutBox>

## Non-goals

The API is deliberately limited. It does **not**:

- **Hold keys.** No secret key is configured or stored. The only account it
  knows about, `RWA_READ_SOURCE`, is a public address used as the unsigned
  source of simulated view calls.
- **Sign or submit transactions.** Every contract read is a
  `simulateTransaction` envelope with an empty signature set that is never
  sent to the network. Every route is a `GET`; there is no write endpoint.
- **Change on-chain state.** Issuing, transferring, allowlisting and dividend
  claims all happen through the web app, signed by the user's wallet (see
  [Integration Guide](/docs/integration)).
- **Act as the source of truth.** It is a ~10-second-old in-memory cache of
  the Soroban ledger, with no database.

**Trust implication:** compromising the API cannot move funds, change an
allowlist, or authorize anything on-chain — there is nothing to steal and no
signing path to abuse. The worst a faulty or malicious API can do is serve
stale or incorrect data, so verify anything security-critical against the
ledger directly before acting on it. See
[Architecture](/docs/architecture) for how this fits the wider system.

## How indexing works

A background task polls **Soroban RPC** every 10 seconds. On each tick it reads the
current state of the four contracts by *simulating* view calls — `simulateTransaction`
is the Soroban RPC method that runs a contract function read-only, without submitting
a transaction to the network. It calls `get_all_assets`
on the registry, then per-asset `get_metadata`, `get_allowlist`, `balance` and
`get_distributions_for_asset` — and rebuilds an in-memory snapshot. The results are
decoded from `ScVal` (Stellar Contract Value — the binary format Soroban uses to
return data from contracts). For the full
polling model and what it means for data freshness, see
[How the indexer rebuilds state](/docs/architecture#how-the-indexer-rebuilds-state).

<CalloutBox variant="note">
State is kept **in memory** (no database in v1). If the RPC is briefly
unreachable, the indexer logs the error, keeps serving the last good snapshot, and
retries on the next tick. The API never panics on a transient failure.
</CalloutBox>

## Operational details

### Authentication and rate limiting

There is currently **no authentication** required to call the data endpoints
(everything under `/v1`, plus `/`, `/version` and `/health`). The one exception
is the operator-only [`/metrics`](#metrics-endpoint) endpoint, which requires a
bearer token.

The API applies request throttling, and its `/v1` data routes support HTTP
caching with `Cache-Control` and ETags. The `X-RateLimit-*` response headers
described in the reference are planned; caching is already available:

<CalloutBox variant="tip">
See <a href="/docs/api/rate-limits">Rate Limits &amp; Caching</a> for the
active ETag conditional-request flow and cache headers, along with the planned
rate-limit response headers and polling recommendations.
</CalloutBox>

### Data freshness and caching

The API refreshes its in-memory state approximately **every 10 seconds** by polling
Soroban RPC. This means:

- Data lags the ledger by ~10 seconds on average.
- Two requests made within the same 10-second window will return identical data.
- If Soroban RPC is temporarily unreachable, the API continues serving the last
  successful snapshot (no error, just stale data).

For integrations where you need real-time data, consider reading contracts directly
via Soroban RPC.

### Metrics endpoint

`GET /metrics` exposes indexer health in the
[Prometheus text exposition format](https://prometheus.io/docs/instrumenting/exposition_formats/)
(`Content-Type: text/plain; version=0.0.4`). It is intended for operators, not
API consumers, and is **not** part of the `/v1` namespace or its stability
promise.

#### Authentication

The endpoint is protected by a static bearer token configured on the server:

| Environment variable | Purpose |
|----------------------|---------|
| `RWA_METRICS_TOKEN` | Shared secret that scrapers must present. |

Scrapers send it in the `Authorization` header:

```bash
curl -H "Authorization: Bearer $RWA_METRICS_TOKEN" http://localhost:8080/metrics
```

- The header must be exactly `Bearer <token>`; the token is compared verbatim.
- A missing, malformed or wrong token returns `401 Unauthorized` with the plain
  text body `metrics authentication required`.
- If `RWA_METRICS_TOKEN` is **unset or empty**, the endpoint is disabled and
  every request returns `401`. There is no way to expose metrics without a token.
- The variable is read on every request, but since it comes from the process
  environment, rotating it means restarting the API with the new value.

<CalloutBox variant="warning">
Treat <code>RWA_METRICS_TOKEN</code> like any other secret: generate a long random
value (for example <code>openssl rand -hex 32</code>), keep it out of source control,
and serve the API over TLS so the token is not sent in clear text.
</CalloutBox>

#### Exposed metrics

| Metric | Type | Labels | Description |
|--------|------|--------|-------------|
| `rwa_indexer_refresh_duration_seconds` | summary | — | Wall-clock time of each indexer refresh (one sample per poll tick, successful or not). Rendered with `quantile` series plus `_sum` and `_count`. |
| `rwa_indexer_refresh_total` | counter | `outcome` = `success` \| `failure` | Number of completed refresh attempts. A failure means the whole tick failed and the previous snapshot kept being served. |
| `rwa_indexer_asset_read_errors_total` | counter | `asset_id`, `read` = `get_metadata` \| `compliance` \| `dividends` \| `dividend_decode` | Per-asset RPC reads that failed during an otherwise successful refresh. |

Series only appear after they are first recorded, so a freshly started API may
return an empty body until the first refresh completes, and
`rwa_indexer_asset_read_errors_total` is absent until a read actually fails.

Useful alert starting points:

```promql
# Refreshes are failing
rate(rwa_indexer_refresh_total{outcome="failure"}[5m]) > 0

# No successful refresh in the last minute (normal cadence is ~10s)
increase(rwa_indexer_refresh_total{outcome="success"}[1m]) == 0

# A specific asset keeps failing to read
increase(rwa_indexer_asset_read_errors_total[15m]) > 0
```

For snapshot age, use `GET /health`, which returns `503` with
`"status": "degraded"` once the snapshot is older than three poll intervals.

#### Example scrape configuration

Store the token in a file readable by Prometheus and reference it with
`credentials_file`, so it never appears in the config itself:

```yaml
scrape_configs:
  - job_name: stellar-rwa-api
    scrape_interval: 15s
    metrics_path: /metrics
    scheme: https
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/secrets/rwa-metrics-token
    static_configs:
      - targets: ["rwa-api.example.com"]
```

A scrape interval of 10–15 seconds matches the indexer's poll cadence; scraping
faster does not yield new data.

## Versioning and stability

All data endpoints are served under the `/v1` prefix (for example
`GET /v1/assets/:id`). The path prefix is the compatibility contract: a client
written against `/v1` should keep working, unmodified, for as long as `/v1` is
served. `GET /version` returns the running server version so clients can log or
report it, but clients should not need to branch on it.

### What `/v1` covers

The stability promise applies to every route under `/v1`, including its path and
query parameters, response JSON shapes, field types and meanings, HTTP status
codes, and the [error body](#error-responses) format and `error` codes.

It does **not** cover operator-facing routes (`/metrics`, `/health`, `/`), the
exact values of rate-limit budgets, the indexing interval, or anything marked as
experimental or planned in these docs.

### Changes that may ship without a version bump

These are **additive** or behavioural changes that a well-behaved client already
tolerates. Clients must ignore unknown fields and unknown enum values to benefit
from them.

- Adding new endpoints under `/v1`.
- Adding new **optional** query parameters with a default that preserves the
  current behaviour.
- Adding new fields to response objects.
- Adding new values to open-ended string enums (for example a new event type or
  a new `error` code for a previously unhandled case).
- Adding new response headers.
- Changing the wording of human-readable `message` strings.
- Changing ordering where the order is not documented as guaranteed.
- Tuning operational limits (rate limits, timeouts, body size, poll interval)
  and fixing bugs so behaviour matches the documentation.

### Changes that require a new version

These are **breaking** and will only ship under a new prefix (`/v2`):

- Removing or renaming an endpoint, field, or query parameter.
- Changing a field's type or encoding (for example turning a decimal string
  such as `total_supply` into a number) or its units (for example cents to
  dollars).
- Making an optional parameter required, or changing a default in a way that
  alters results.
- Changing the status code or `error` code returned for an existing condition.
- Changing the meaning of an existing field or the semantics of an endpoint.
- Changing pagination, ETag, or error-body structure.

### Deprecation policy

- When `/v2` is introduced, `/v1` keeps running alongside it; the two are
  served from the same process and index.
- A deprecation is announced in these docs and the changelog before anything is
  removed, and `/v1` remains available for **at least 6 months** after `/v2` is
  generally available.
- Individual `/v1` fields or endpoints may be marked deprecated in the docs and
  the OpenAPI spec (`deprecated: true`) ahead of time, but are not removed from
  `/v1` itself.
- Security fixes may change behaviour without notice when there is no
  compatible alternative; such changes will be called out in the changelog.

## Amount units and conventions

All monetary amounts and token supplies in the API reference adhere to strict unit rules that agree with the underlying Soroban contracts:

- **Large integers are strings.** Token amounts, valuations, balances, and dividend pools are 128-bit signed integers (`i128`) on-chain. To eliminate precision loss in JavaScript and other IEEE 754 floating-point runtimes, they are serialized as decimal **strings** (`total_supply`, `valuation_cents`, `tvl_cents`, `balance`, `total_amount`, `distributed`).
- **Valuations are USD cents.** `valuation_cents` (on assets) and `tvl_cents` (on stats) represent valuations in **USD cents** (`1 USD = 100 cents`). To convert to dollar display values, divide by 100:
  ```typescript
  const cents = BigInt(asset.valuation_cents); // "500000000"
  const dollars = Number(cents) / 100; // 5000000.00 ($5,000,000.00)
  ```
- **Convenience floats.** For quick display and charting, valuations also provide a `valuation_usd` and `tvl_usd` (`f64` US dollars), and percentages are given as numbers (`share_percent`, `claimed_percent`).
- **Token amounts are in the token's own decimals base.** Asset balances (`balance`) and supplies (`total_supply`) are given as raw integer base units. Divide by `10 ** decimals` (where `decimals` is the asset's configured decimal places, e.g. `2` or `7`):
  ```typescript
  const rawSupply = BigInt(asset.total_supply); // "1000000"
  const displaySupply = Number(rawSupply) / (10 ** asset.decimals); // 10000.00
  ```
- **Dividend pools use payment-token base units.** In dividend distributions, `total_amount`, `distributed`, and claimable shares are measured in base units of the **payment token** (e.g. Classic Stellar assets / SAC tokens like USDC typically use 7 decimals):
  ```typescript
  const rawDividend = BigInt(distribution.total_amount); // "100000000000"
  const paymentDecimals = 7;
  const displayDividend = Number(rawDividend) / (10 ** paymentDecimals); // 10000.0 USDC
  ```

| Amount field | Format | Unit | Conversion to display |
|---|---|---|---|
| `valuation_cents` | string (`i128`) | USD cents | `Number(BigInt(valuation_cents)) / 100` |
| `valuation_usd` | number (`f64`) | USD dollars | Already in USD |
| `tvl_cents` | string (`i128`) | USD cents | `Number(BigInt(tvl_cents)) / 100` |
| `tvl_usd` | number (`f64`) | USD dollars | Already in USD |
| `total_supply` | string (`i128`) | Asset token base units | `Number(BigInt(total_supply)) / 10 ** decimals` |
| `balance` | string (`i128`) | Asset token base units | `Number(BigInt(balance)) / 10 ** decimals` |
| `total_amount` | string (`i128`) | Payment token base units | `Number(BigInt(total_amount)) / 10 ** payment_decimals` |
| `distributed` | string (`i128`) | Payment token base units | `Number(BigInt(distributed)) / 10 ** payment_decimals` |

## Health endpoint

`GET /health` reports the liveness and readiness of the API. It is the right probe to use for deciding whether the service can serve useful data.

| HTTP status | `"status"` field | Meaning |
|-------------|-----------------|---------|
| `200 OK` | `"ok"` | The indexer is polling normally and the snapshot is fresh. |
| `503 Service Unavailable` | `"degraded"` | The snapshot is stale — no successful poll within the last `max_age_seconds`. |

The `503` condition fires in two situations:
1. **Before the first successful poll.** The API process is alive but has not yet indexed any data. It can accept requests but cannot return useful results. This makes `GET /health` behave like a **readiness probe**, not just a liveness probe — use it to delay traffic until the first snapshot is ready.
2. **After an extended RPC outage.** If the indexer fails to poll for longer than `max_age_seconds` (default: 30 seconds — three poll intervals), the health status flips to `degraded` and stale headers are added to every response.

**Suitability as a readiness probe:** Yes. Do not route traffic to a new instance until `GET /health` returns `200`. This ensures the first request served against the instance hits a populated snapshot, not an empty one.

**Suitability as a liveness probe:** Use with care. Because `GET /health` returns `503` during extended RPC outages, a strict liveness probe configured on this endpoint would restart the process when the RPC is temporarily down — usually the wrong behaviour. A dedicated liveness probe at `/` (which always returns `200`) is more appropriate if you need separate liveness and readiness signals.

**Example response:**

```bash
curl http://localhost:8080/health
```

```json
{
  "status": "ok",
  "snapshot_age_seconds": 4,
  "max_age_seconds": 30,
  "consecutive_failures": 0,
  "last_poll_at": "2026-07-09T08:43:12.101772791+00:00",
  "last_poll_age_seconds": 4,
  "last_indexed_ledger": 3514152,
  "ledger_lag": 1
}
```

For the full field reference and staleness headers, see [API · Health & Indexer Lag](/docs/api/health).

## Error responses

Every error response — from route handlers, unknown routes and methods, query or
path rejections, request timeouts, oversized bodies, the rate limiter, and
`/metrics` authentication — is normalized to one shared JSON shape with
`Content-Type: application/json`:

```json
{
  "error": "not_found",
  "message": "no asset with id 999"
}
```

`error` is a stable, machine-readable code you can branch on; `message` is a
human-readable explanation whose wording may change without notice. Clients
should ignore unknown fields and unknown `error` codes.

**Common errors:**

| HTTP status | `error` code | Meaning |
|--------------|--------------|---------|
| `400 Bad Request` | `bad_request` | A path parameter or query value cannot be parsed, such as a non-numeric asset `:id` or malformed pagination value. |
| `401 Unauthorized` | `unauthorized` | `/metrics` was called without a valid bearer token. |
| `404 Not Found` | `not_found` | The requested asset or distribution does not exist, or the URL does not match any route. |
| `405 Method Not Allowed` | `method_not_allowed` | The route exists but does not support the request method (all data routes are `GET`). |
| `408 Request Timeout` | `request_timeout` | The request took too long to be received or processed. |
| `413 Payload Too Large` | `payload_too_large` | The request body exceeded the server's size limit. |
| `429 Too Many Requests` | `rate_limited` | The per-IP rate limit was exceeded. See [Rate Limits & Caching](/docs/api/rate-limits) for backoff guidance. |
| `500 Internal Server Error` | `internal_error` | An unexpected server failure occurred. Report persistent failures. |
| `503 Service Unavailable` | `service_unavailable` | The service cannot serve useful data yet, for example before the first successful index refresh. |

<CalloutBox variant="note">
The health endpoint is the one exception to the error shape: `GET /health`
returns its own status document (with `"status": "degraded"` and
`snapshot_age_seconds` / `max_age_seconds`) when the snapshot is stale. See
<a href="/docs/api/health">Health &amp; Indexer Lag</a>.
</CalloutBox>

The two-field body above is the single canonical error schema for the whole API.
For the full list of codes, their exact statuses, and client handling guidance,
see [API · Errors](/docs/api/errors).

## CORS

The API is designed to be called directly from a browser, so the docs site and
the web app can fetch it without a proxy. The policy is permissive:

| CORS setting | Value | Notes |
|---|---|---|
| `Access-Control-Allow-Origin` | `*` | Any origin may call the API. |
| `Access-Control-Allow-Methods` | `GET`, `OPTIONS` | Every data route is a `GET`; `OPTIONS` answers preflight requests. |
| `Access-Control-Allow-Headers` | `*` | Any request header is accepted, including `If-None-Match` and `Authorization`. |
| `Access-Control-Expose-Headers` | `ETag`, `Cache-Control`, `X-RateLimit-*` | Readable from JavaScript via `response.headers.get(...)`. |
| `Access-Control-Allow-Credentials` | *not set* | Cookies and other credentials are **not** supported. |
| `Access-Control-Max-Age` | `86400` | Preflight results may be cached by the browser for 24 hours. |

<CalloutBox variant="warning">
Because <code>Access-Control-Allow-Credentials</code> is not sent, the browser
will not attach cookies or HTTP auth credentials to cross-origin requests, and
<code>fetch(..., {"{"} credentials: "include" {"}"})</code> will fail. The API
requires no authentication for data routes, so call it without credentials.
</CalloutBox>

A minimal browser request:

```javascript
const res = await fetch(`${API_BASE_URL}/v1/stats`, {
  method: "GET",
  headers: { Accept: "application/json" },
  // Do NOT use credentials: "include" — the API does not allow credentials.
});

if (!res.ok) throw new Error(`API error: ${res.status}`);
const stats = await res.json();
console.log(stats.tvl_usd);
```

## Conditional requests (ETag / If-None-Match)

`/v1` responses carry an `ETag` derived from the indexed snapshot. Send it back
in `If-None-Match` and the API answers `304 Not Modified` with an empty body
when nothing has changed, saving bandwidth and JSON parsing. Because the
snapshot refreshes roughly every 10 seconds, a repeat request within the same
window will normally return `304`.

A full round-trip with `curl`:

```bash
# 1. First request — 200 OK with an ETag
curl -i http://localhost:8080/v1/stats
```

```http
HTTP/1.1 200 OK
content-type: application/json
cache-control: public, max-age=10
etag: "a1b2c3d4e5f6"

{"total_assets":1,"active_assets":1,"tvl_cents":"500000000", ...}
```

```bash
# 2. Repeat with the ETag — 304 Not Modified, no body
curl -i http://localhost:8080/v1/stats \
  -H 'If-None-Match: "a1b2c3d4e5f6"'
```

```http
HTTP/1.1 304 Not Modified
cache-control: public, max-age=10
etag: "a1b2c3d4e5f6"
```

The `ETag` value must be sent back **exactly** as received, including the
surrounding double quotes. Once the indexer picks up a new ledger the `ETag`
changes and the next conditional request returns `200` with the fresh body.

See <a href="/docs/api/rate-limits">Rate Limits &amp; Caching</a> for the full
caching model, cache header semantics and polling recommendations.
</CalloutBox>

## `/stats` response

```json
{
  "total_assets": 1,
  "active_assets": 1,
  "tvl_cents": "500000000",
  "tvl_usd": 5000000.0,
  "total_holders": 1,
  "total_distributions": 0,
  "last_indexed_ledger": 3514152,
  "last_updated": "2026-07-09T08:43:12.101772791+00:00"
}
```

**Response schema:**

| Field | Type | Unit / Description |
|---|---|---|
| `total_assets` | number | Total number of assets registered in the registry contract |
| `active_assets` | number | Count of active assets |
| `tvl_cents` | string | Total value locked across active assets in **USD cents** (`i128` string). Divide by 100 for USD dollars. |
| `tvl_usd` | number | Total value locked in **USD dollars** (`f64` float convenience field, equal to `tvl_cents / 100`) |
| `total_holders` | number | Count of distinct approved addresses with a positive balance across all assets |
| `total_distributions` | number | Total dividend distributions created across all assets |
| `last_indexed_ledger` | number | Most recent ledger read by the indexer |
| `last_updated` | string or null | RFC 3339 timestamp of the last successful index refresh |

`total_holders` is the count of **distinct approved addresses** across all assets;
`last_indexed_ledger` is the ledger the most recent successful refresh read from.

**Response schema** (`Stats`):

| Field | Type | Unit | Nullable | Description |
|-------|------|------|----------|-------------|
| `total_assets` | integer | Assets | No | Total indexed assets |
| `active_assets` | integer | Assets | No | Indexed assets marked active |
| `tvl_cents` | string | USD cents | No | Exact TVL as a decimal string |
| `tvl_usd` | number | USD | No | TVL in dollars |
| `total_holders` | integer | Distinct addresses | No | Addresses with a positive token balance across assets |
| `total_distributions` | integer | Distributions | No | Total indexed dividend distributions |
| `last_indexed_ledger` | integer | Ledger sequence | No | Ledger read by the last successful full refresh |
| `last_updated` | string | RFC 3339 timestamp | Yes | JSON `null` before a successful refresh |
