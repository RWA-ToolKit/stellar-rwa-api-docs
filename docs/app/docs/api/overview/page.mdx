# API Overview

The Stellar RWA API is a **read-only** REST service that indexes all tokenized
asset activity on Stellar and serves it as JSON. It is written in Rust (Axum +
tokio) and holds no keys — it never signs or submits transactions.

Base URL (local): `http://localhost:8080`

## How indexing works

A background task polls **Soroban RPC** every 10 seconds. On each tick it reads the
current state of the four contracts by *simulating* view calls — `get_all_assets`
on the registry, then per-asset `get_metadata`, `get_allowlist`, `balance` and
`get_distributions_for_asset` — and rebuilds an in-memory snapshot.

<CalloutBox variant="note">
State is kept **in memory** (no database in v1). If the RPC is briefly
unreachable, the indexer logs the error, keeps serving the last good snapshot, and
retries on the next tick. The API never panics on a transient failure.
</CalloutBox>

## Conventions

- **Large integers are strings.** Token amounts and valuations are `i128`
  on-chain. To avoid precision loss in JavaScript, they are serialized as decimal
  **strings** (`total_supply`, `valuation_cents`, `balance`, `total_amount`).
- **Convenience floats.** Valuations also include a `valuation_usd` (float
  dollars) and percentages (`share_percent`, `claimed_percent`) for display.
- **Amounts are raw base units.** Divide by `10 ** decimals` to get a display
  value. The asset's `decimals` is included on each asset.
- **Cents.** `valuation_cents` is USD cents; `valuation_usd = valuation_cents / 100`.

## Errors

Errors return an appropriate HTTP status and a JSON body:

```json
{ "error": "not_found", "message": "no asset with id 999" }
```

| Status | `error` | When |
|--------|---------|------|
| `404` | `not_found` | Unknown asset id |
| `400` | — | Non-numeric `:id` path (rejected by the router) |

## CORS

All origins, methods and headers are allowed, so the docs site and the web app
can call the API directly from the browser.

## `/stats` response

```json
{
  "total_assets": 1,
  "active_assets": 1,
  "tvl_cents": "500000000",
  "tvl_usd": 5000000.0,
  "total_holders": 1,
  "total_distributions": 0,
  "last_indexed_ledger": 3514152,
  "last_updated": "2026-07-09T08:43:12.101772791+00:00"
}
```

`total_holders` is the count of **distinct approved addresses** across all assets;
`last_indexed_ledger` is the ledger the most recent successful refresh read from.

## Data freshness

Every response backed by the indexer's in-memory snapshot can be stale by up to
one polling cycle (`POLL_INTERVAL`, currently **10 seconds** — see
`api/src/indexer/mod.rs`). Two fields on `GET /stats` tell you exactly how stale
the data you're looking at is:

- **`last_updated`** — an RFC 3339 timestamp of the last *successful* index
  refresh (`api/src/indexer/mod.rs`, around the `last_updated: Some(chrono::Utc::now().to_rfc3339())`
  assignment). Compare it against the current time to compute data age directly.
- **`last_indexed_ledger`** — the Stellar ledger sequence the snapshot was built
  from. Two responses with the same `last_indexed_ledger` are guaranteed to have
  identical bodies.

<CalloutBox variant="note">
If the indexer's RPC calls fail, it keeps serving the **last good snapshot**
rather than erroring — `last_updated` simply stops advancing. A consumer that
needs to detect this should treat a `last_updated` older than a few multiples of
`POLL_INTERVAL` as a sign the indexer is degraded, even though every endpoint
still returns `200 OK`.
</CalloutBox>

`last_indexed_ledger` also drives the `ETag` and `Cache-Control: max-age=10`
headers on every snapshot-backed endpoint (`api/src/routes/mod.rs`,
`cache_headers`/`insert_cache_headers`): send `If-None-Match` with the previous
`ETag` to get a cheap `304 Not Modified` when nothing has changed since your
last request.
