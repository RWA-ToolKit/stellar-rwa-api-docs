# API Overview

The Stellar RWA API is a **read-only** REST service that indexes all tokenized
asset activity on Stellar and serves it as JSON. It is written in Rust (Axum +
tokio) and holds no keys — it never signs or submits transactions.

Base URL (local): `http://localhost:8080`

## How indexing works

A background task polls **Soroban RPC** every 10 seconds. On each tick it reads the
current state of the four contracts by *simulating* view calls — `get_all_assets`
on the registry, then per-asset `get_metadata`, `get_allowlist`, `balance` and
`get_distributions_for_asset` — and rebuilds an in-memory snapshot.

<CalloutBox variant="note">
State is kept **in memory** (no database in v1). If the RPC is briefly
unreachable, the indexer logs the error, keeps serving the last good snapshot, and
retries on the next tick. The API never panics on a transient failure.
</CalloutBox>

## Conventions

- **Large integers are strings.** Token amounts and valuations are `i128`
  on-chain. To avoid precision loss in JavaScript, they are serialized as decimal
  **strings** (`total_supply`, `valuation_cents`, `balance`, `total_amount`).
- **Convenience floats.** Valuations also include a `valuation_usd` (float
  dollars) and percentages (`share_percent`, `claimed_percent`) for display.
- **Amounts are raw base units.** Divide by `10 ** decimals` to get a display
  value. The asset's `decimals` is included on each asset.
- **Cents.** `valuation_cents` is USD cents; `valuation_usd = valuation_cents / 100`.

## Errors

Errors return an appropriate HTTP status and a JSON body:

```json
{ "error": "not_found", "message": "no asset with id 999" }
```

| Status | `error` | When |
|--------|---------|------|
| `404` | `not_found` | Unknown asset id |
| `400` | — | Non-numeric `:id` path (rejected by the router) |

## CORS

The API only answers cross-origin browser requests from an **allowlist of
origins**. Everything else about the policy is fixed in code:

| Setting | Value |
| --- | --- |
| Allowed origins | `RWA_CORS_ALLOWED_ORIGINS`, default `http://localhost:3000` |
| Allowed methods | `GET` |
| Allowed request headers | `Content-Type`, `If-None-Match` |
| Exposed response headers | `ETag`, `Retry-After`, `Cache-Control` |

### Configuring allowed origins

Set `RWA_CORS_ALLOWED_ORIGINS` in the API's environment as a comma-separated list
(whitespace around commas is trimmed). `api/.env.example` ships it commented
out. Uncomment it in your `api/.env` and list your origins:

```bash
# api/.env
RWA_CORS_ALLOWED_ORIGINS=http://localhost:3000,https://docs.example.com
```

- If the variable is unset, only `http://localhost:3000` is allowed.
- Setting it **replaces** the default. Include `http://localhost:3000` again if
  you still need it.
- Matching is exact: scheme, host and port must be identical, with no trailing
  slash or path. `http://localhost:3000` does not match `http://127.0.0.1:3000`
  or `http://localhost:3000/`.
- `*` is not supported, and neither is a value that is not a valid header. Both
  make the API panic on startup.

### What a rejected origin looks like

CORS is enforced by the browser, not the server. The API never returns a `4xx`
or a JSON error body for a disallowed origin. It just leaves out
`Access-Control-Allow-Origin`.

A preflight (`OPTIONS`) from an **allowed** origin:

```bash
curl -i -X OPTIONS http://localhost:8080/v1/stats \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: if-none-match"
```

```http
HTTP/1.1 200 OK
access-control-allow-origin: http://localhost:3000
access-control-allow-methods: GET
access-control-allow-headers: content-type,if-none-match
vary: origin, access-control-request-method, access-control-request-headers
```

The same preflight from a **rejected** origin
(`-H "Origin: https://evil.example"`) is still `200 OK` with an empty body and
the same `allow-methods` / `allow-headers`, but has **no
`access-control-allow-origin`**. A plain cross-origin `GET` from a rejected
origin works the same way. The server runs the request and returns the normal
`200` JSON, without the allow-origin header.

In the browser, this shows up as:

- a console error like *"…has been blocked by CORS policy: No
  'Access-Control-Allow-Origin' header is present on the requested resource"*;
- `fetch()` rejecting with `TypeError: Failed to fetch` (Firefox:
  `NetworkError when attempting to fetch resource`). You never get a `Response`
  object, so you can't read the status, headers or body from JavaScript.

curl, server-side code and other non-browser clients ignore CORS, so they are
unaffected. CORS limits which web pages can read responses. It is not access
control.

### Fix checklist

1. Copy the exact origin from the browser's request `Origin` header (DevTools →
   Network), including scheme and port.
2. Add it to `RWA_CORS_ALLOWED_ORIGINS`, keeping any origins you still need.
3. Restart the API. The list is only read at startup.
4. Re-run the `OPTIONS` curl above with your origin and check that
   `access-control-allow-origin` echoes it back.
5. If the preflight passes but the request still fails, check that you only
   use `GET` and only set `Content-Type` / `If-None-Match`. Any other method or
   custom header is not allowed.

## `/stats` response

```json
{
  "total_assets": 1,
  "active_assets": 1,
  "tvl_cents": "500000000",
  "tvl_usd": 5000000.0,
  "total_holders": 1,
  "total_distributions": 0,
  "last_indexed_ledger": 3514152,
  "last_updated": "2026-07-09T08:43:12.101772791+00:00"
}
```

`total_holders` is the count of **distinct approved addresses** across all assets;
`last_indexed_ledger` is the ledger the most recent successful refresh read from.

### Python example

Requires `pip install requests`. The output below uses the sample values from the
response above.

```python
import requests

resp = requests.get("http://localhost:8080/stats", timeout=10)
resp.raise_for_status()
stats = resp.json()

print(f"Assets: {stats['active_assets']}/{stats['total_assets']} active")
print(f"TVL: ${stats['tvl_usd']:,.2f}")
print(f"Holders: {stats['total_holders']}")
```

Expected output:

```text
Assets: 1/1 active
TVL: $5,000,000.00
Holders: 1
```

## FAQ

### Why REST instead of GraphQL?

The API only exposes a handful of fixed, shallow resources — assets, their
holders, compliance summary and dividend history — so there is no deeply nested
or client-varying query shape that GraphQL's flexible querying would pay for.
REST also keeps the service dependency-free (no schema/resolver layer) and makes
every response cacheable and curl-able with a plain URL, which matches the
read-only, polling nature of the indexer. If a future version needs to let
clients compose across many related resources in one round trip, GraphQL would
be reconsidered then — for now it would add complexity without solving a real
problem for this API's shape.
