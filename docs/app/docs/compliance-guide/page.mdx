# Compliance Guide

<LastReviewed date={metadata.lastReviewed} />

Compliance is what separates a **real-world asset platform** from a plain token
factory. Anyone can mint a token; the hard part — and the regulated part — is
controlling **who is allowed to hold it**. This guide explains the compliance
model end to end: why it exists, how the allowlist works, how the on-chain
transfer gate is enforced, and how issuers should operate it.

## Why compliance matters for RWA

A real-world asset — equity in a building, a trade invoice, a warehouse of copper —
is almost always a **regulated instrument**. The law in most jurisdictions
restricts who may own it: accredited investors only, residents of permitted
countries only, parties who have cleared KYC/AML checks only.

If those restrictions live only in a web app, they are worthless — anyone can call
the contract directly and bypass the UI. For a token to credibly represent a
regulated asset, the restriction must be enforced **by the asset itself**, at the
protocol level, on every transfer. That is exactly what this platform does.

<CalloutBox variant="compliance" title="The one-sentence model">
An RWA token can only ever be held by an address the issuer has explicitly
approved — and the token enforces that on-chain, on every single transfer, by
asking a separate compliance contract for permission.
</CalloutBox>

## How the allowlist model works

The [compliance contract](/docs/contracts/compliance) maintains a **KYC allowlist**:
a set of `KycRecord`s, one per address. A `KycRecord` is the on-chain struct that
stores everything the compliance contract knows about one address. Each record carries:

- a **status** — `Approved`, `Pending`, `Rejected`, or `Suspended`
- a **jurisdiction** — an ISO country code (`US`, `KE`, `DE`, …)
- a **`verified_at`** ledger and an **`expires_at`** ledger (`0` = never expires)

Only the compliance **admin** (the issuer or their compliance officer) can change
the allowlist, via `add_to_allowlist`, `suspend`, and `remove`. Adding an address
sets its status to `Approved`; suspending flips it to `Suspended` but keeps the
record for audit; removing deletes it entirely.

An address is permitted to hold or receive the asset **only if `is_allowed`
returns `true`**, which requires all three of:

1. status is `Approved`,
2. the approval has not expired, and
3. the address's jurisdiction is not blocked.

## How transfer gating works

This is the mechanism that makes the whole thing enforceable. The asset-token
contract does not trust any off-chain system; on every `transfer` it makes
**cross-contract calls** into the compliance contract for *both* parties:

```
transfer(from, to, amount)
  ├─ from.require_auth()
  ├─ assert !paused
  ├─ compliance.is_allowed(from)   ── cross-contract call ──▶ compliance contract
  ├─ compliance.is_allowed(to)     ── cross-contract call ──▶ compliance contract
  └─ move balances + emit event
```

The same gate as a sequence. The sender is checked first, so a transfer
between two non-approved addresses fails with `SenderNotCompliant` and the
recipient check never runs:

```text
Caller             Asset token                     Compliance contract
  │                    │                                    │
  │ transfer(from,     │                                    │
  │   to, amount) ───▶ │                                    │
  │                    │ from.require_auth(), assert !paused│
  │                    │                                    │
  │                    │ is_allowed(from) ────────────────▶ │
  │                    │ ◀──────────────────── true | false │
  │                    │                                    │
  │                    ├─ false ─▶ revert SenderNotCompliant (7)
  │                    │           (no balance change, no event)
  │                    │                                    │
  │                    │ is_allowed(to) ──────────────────▶ │
  │                    │ ◀──────────────────── true | false │
  │                    │                                    │
  │                    ├─ false ─▶ revert RecipientNotCompliant (8)
  │                    │           (no balance change, no event)
  │                    │                                    │
  │                    │ both true: move balances,          │
  │ ◀──────── ok ───── │ emit transfer event                │
```

If either `is_allowed` returns `false`, the transaction **reverts** — no balance
moves, no event is emitted, the transfer simply cannot happen. The same check gates
`mint` on the recipient, so tokens can never be minted into a non-approved wallet
in the first place.

Because the asset token depends only on the compliance **interface**
(`is_allowed`), the concrete compliance contract can be swapped with
`set_compliance` — for example to migrate to a stricter policy — without
redeploying the token.

<CalloutBox variant="tip" title="Verify it yourself">
Try to transfer the sample asset to an address that isn't on the allowlist. The
transaction fails with <code>RecipientNotCompliant (8)</code>. That failure is the
product working — the gate is doing its job.
</CalloutBox>

### What a failed gate looks like

| Contract error | Meaning |
|----------------|---------|
| `SenderNotCompliant (7)` | The `from` address failed `is_allowed` |
| `RecipientNotCompliant (8)` | The `to` address failed `is_allowed` |
| `Paused (6)` | Transfers are globally halted by the issuer |

## Jurisdiction restrictions

Beyond per-address control, issuers can block entire **jurisdictions**. Calling
`block_jurisdiction("US")` makes every approved address whose record says `US` fail
`is_allowed` immediately — without editing a single individual record. Unblocking
with `unblock_jurisdiction("US")` restores them.

This models a common real-world requirement: a regulatory change, sanction, or
offering restriction that must apply to a whole country at once. Because the check
happens inside `is_allowed` at read time, the effect is **instantaneous and
retroactive** — there is no list to re-scan and no window where stale approvals
still work.

The API's [`/assets/:id/compliance`](/docs/api/compliance) endpoint surfaces the
jurisdiction distribution (as counts) so issuers can audit their geographic
exposure before making such a change.

## KYC expiry and suspension

Approvals are not forever. Two mechanisms let issuers keep the allowlist current:

- **Expiry.** `add_to_allowlist` takes an `expires_at` ledger. Once the current
  ledger reaches it, `is_allowed` returns `false` automatically — the holder can no
  longer transfer, and cannot receive more, until re-approved. An `expires_at` of
  `0` means the approval never expires. Because time is measured in **ledger
  sequence numbers** (~5 seconds each), a one-year approval is roughly
  `+6,300,000` ledgers from now.

- **Suspension.** `suspend(address)` sets the status to `Suspended` while keeping
  the record. This is the right tool for a temporary hold — a pending re-review, a
  compliance flag — because it is reversible with `add_to_allowlist` and preserves
  the audit trail. Use `remove` only when an address should be erased entirely.

<CalloutBox variant="warning" title="Expiry is enforced on read, not on a timer">
There is no background job expiring records. The check is evaluated live against
the current ledger every time `is_allowed` runs. An approval that lapsed one second
ago fails the very next transfer — no cron, no lag.
</CalloutBox>

## Worked scenarios

These examples show how the live `is_allowed` gate affects a transfer. A transfer
checks both the sender and recipient, so the error identifies which side failed.

| Scenario | What the issuer or integrator sees | Outcome and next step |
|----------|------------------------------------|-----------------------|
| **Unapproved recipient** | An address has no allowlist record, or its status is `Pending` or `Rejected`. `is_allowed(recipient)` returns `false`. | The transfer reverts with `RecipientNotCompliant (8)`. Complete verification, then approve the recipient with `add_to_allowlist`; retry only after the approval is in effect. |
| **Expired approval** | The record still says `Approved`, but the current ledger has reached `expires_at`. | `is_allowed` returns `false`, and an outgoing transfer fails with `SenderNotCompliant (7)`; an incoming transfer fails with `RecipientNotCompliant (8)`. Re-verify the holder and issue a new approval with a future expiry. |
| **Suspended holder** | The holder's record is retained for the audit trail but has status `Suspended`. | `is_allowed` returns `false`. The holder cannot send (`SenderNotCompliant (7)`) or receive (`RecipientNotCompliant (8)`) until the compliance admin resolves the review and approves them again. |
| **Blocked jurisdiction** | The address has an otherwise valid approval, but its recorded jurisdiction is currently blocked. | The jurisdiction check makes `is_allowed` return `false` immediately. Transfers from that holder fail with `SenderNotCompliant (7)` and transfers to them fail with `RecipientNotCompliant (8)`. Review the restriction before unblocking the jurisdiction or changing an individual's record. |

In all four cases, an off-chain status display is not a substitute for the
contract check: use `is_allowed` for the asset's current compliance contract
before submitting a transfer. The transaction itself remains authoritative and
will revert if either party fails the gate.

## Best practices for issuers

1. **Secure the compliance admin key.** It is the single most powerful key in the
   system — it decides who can hold your asset. Use multisig and hardware custody.
2. **Prefer `suspend` over `remove`.** Suspension is reversible and preserves the
   record for audits; removal is destructive.
3. **Set sensible expiries.** Time-bounded approvals force periodic re-KYC and keep
   your allowlist from silently drifting out of date. Choose an expiry that matches
   your re-verification cadence.
4. **Approve the issuer first.** The asset token mints the initial supply to the
   admin, so the admin must be approved on the compliance contract *before*
   `initialize`, or deployment fails with `RecipientNotCompliant`.
5. **Coordinate distributions with balances.** The dividend contract reads balances
   at **claim** time. If you need a clean snapshot, consider pausing the token
   around a distribution window. See the [Dividend contract](/docs/contracts/dividend#security-considerations).
6. **Use jurisdiction blocks deliberately.** They are immediate and affect every
   holder in the region. Review the jurisdiction breakdown from the API first.
7. **Treat registry listing as self-attestation.** Anyone can register an asset;
   the *binding* control is the compliance contract, not the registry entry.

## Putting it together

The compliance contract is small, but it is the reason this platform can represent
regulated assets at all. Every other piece — the token, the registry, the dividend
escrow, the API, the web app — is built around the single invariant it enforces:

> **Only KYC-approved, unexpired, non-blocked addresses can ever hold the asset,
> and the asset enforces this itself on every transfer.**
