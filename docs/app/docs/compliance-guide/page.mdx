# Compliance Guide

<LastReviewed date={metadata.lastReviewed} />

Compliance is what separates a **real-world asset platform** from a plain token
factory. Anyone can mint a token; the hard part — and the regulated part — is
controlling **who is allowed to hold it**. This guide explains the compliance
model end to end: why it exists, how the allowlist works, how the on-chain
transfer gate is enforced, and how issuers should operate it.

## Glossary

New to Stellar or to this platform? These terms recur throughout the guide.

- **RWA (real-world asset)** — a token that represents an off-chain asset such as
  equity, an invoice, or a commodity.
- **KYC / AML** — *Know Your Customer* / *Anti-Money Laundering*: the identity and
  screening checks a regulated issuer must run before letting someone hold an asset.
- **Allowlist** — the set of addresses the issuer has approved to hold the asset.
- **Ledger** — a single Stellar ledger close (roughly 5 seconds). Ledger numbers are
  used here as timestamps: `verified_at` and `expires_at` are ledger numbers, not
  wall-clock times.
- **TTL (time-to-live)** — how many ledgers a piece of on-chain storage stays alive
  before it must be extended. Soroban storage entries (including `KycRecord`s) have
  a TTL; if it lapses the entry is archived and must be restored before use.
- **Footprint** — the set of ledger entries a Soroban transaction reads and writes.
  The footprint must be declared up front so the network can validate the
  transaction; a cross-contract call like `is_allowed` adds the compliance
  contract's entries to the footprint.
- **ScVal** — Soroban's canonical value type (the XDR encoding used for contract
  arguments and return values). Addresses, integers, and structs are all passed as
  `ScVal`s under the hood.
- **SAC (Stellar Asset Contract)** — the built-in contract that wraps a classic
  Stellar asset so it can be used from Soroban. This platform's asset token is a
  custom contract, not a SAC, but both expose a similar `transfer` surface.
- **Passphrase** — the network identifier string (e.g. `Test SDF Network ; September
  2015` for testnet, `Public Global Stellar Network ; September 2015` for mainnet)
  that scopes signatures and transactions to one network. Signing with the wrong
  passphrase produces an invalid transaction.
- **Cross-contract call** — one contract invoking another during a transaction; here
  the asset token calls `is_allowed` on the compliance contract.

## Why compliance matters for RWA

A real-world asset — equity in a building, a trade invoice, a warehouse of copper —
is almost always a **regulated instrument**. The law in most jurisdictions
restricts who may own it: accredited investors only, residents of permitted
countries only, parties who have cleared KYC/AML checks only.

If those restrictions live only in a web app, they are worthless — anyone can call
the contract directly and bypass the UI. For a token to credibly represent a
regulated asset, the restriction must be enforced **by the asset itself**, at the
protocol level, on every transfer. That is exactly what this platform does.

<CalloutBox variant="compliance" title="The one-sentence model">
An RWA token can only ever be held by an address the issuer has explicitly
approved — and the token enforces that on-chain, on every single transfer, by
asking a separate compliance contract for permission.
</CalloutBox>

## How the allowlist model works

The [compliance contract](/docs/contracts/compliance) maintains a **KYC allowlist**:
a set of `KycRecord`s, one per address. A `KycRecord` is the on-chain struct that
stores everything the compliance contract knows about one address. Each record carries:

- a **status** — `Approved`, `Pending`, `Rejected`, or `Suspended`
- a **jurisdiction** — an ISO country code (`US`, `KE`, `DE`, …)
- a **`verified_at`** ledger and an **`expires_at`** ledger (`0` = never expires)

Only the compliance **admin** (the issuer or their compliance officer) can change
the allowlist, via `add_to_allowlist`, `suspend`, and `remove`. Adding an address
sets its status to `Approved`; suspending flips it to `Suspended` but keeps the
record for audit; removing deletes it entirely.

An address is permitted to hold or receive the asset **only if `is_allowed`
returns `true`**, which requires all three of:

1. status is `Approved`,
2. the approval has not expired, and
3. the address's jurisdiction is not blocked.

### Batch allowlist operations

Onboarding a large investor base one call at a time is slow and error-prone. The
compliance contract exposes batch entry points that apply the same validation as
their single-address counterparts, so a partial failure reverts the whole batch:

- `add_to_allowlist_batch(records)` — approve many addresses in one transaction
- `suspend_batch(addresses)` — suspend many addresses at once
- `remove_batch(addresses)` — remove many addresses at once

Each batch is atomic: if any entry is invalid (bad jurisdiction, missing record,
unauthorized caller) the entire call reverts and no record changes. Use batches
for bulk onboarding and bulk offboarding; use the single-address calls for
one-off corrections.

### Admin handover

The compliance admin is the only account that can mutate the allowlist or block
jurisdictions. To transfer that authority — for example when a compliance officer
changes — use the admin handover entry points rather than sharing keys:

- `propose_admin(new_admin)` — the current admin nominates a successor
- `accept_admin()` — the nominee must call this to complete the handover
- `get_admin()` — read the current admin

The two-step handover prevents accidentally handing control to a mistyped or
uncontrolled address: until the nominee accepts, the original admin remains in
control and can cancel by proposing a different successor.

## How transfer gating works

This is the mechanism that makes the whole thing enforceable. The asset-token
contract does not trust any off-chain system; on every `transfer` it makes
**cross-contract calls** into the compliance contract for *both* parties:

```
transfer(from, to, amount)
  ├─ from.require_auth()
  ├─ assert !paused
  ├─ compliance.is_allowed(from)   ── cross-contract call ──▶ compliance contract
  ├─ compliance.is_allowed(to)     ── cross-contract call ──▶ compliance contract
  └─ move balances + emit event
```

The same gate as a sequence. The sender is checked first, so a transfer
between two non-approved addresses fails with `SenderNotCompliant` and the
recipient check never runs:

```text
Caller             Asset token                     Compliance contract
  │                    │                                    │
  │ transfer(from,     │                                    │
  │   to, amount) ───▶ │                                    │
  │                    │ from.require_auth(), assert !paused│
  │                    │                                    │
  │                    │ is_allowed(from) ────────────────▶ │
  │                    │ ◀──────────────────── true | false │
  │                    │                                    │
  │                    ├─ false ─▶ revert SenderNotCompliant (7)
  │                    │           (no balance change, no event)
  │                    │                                    │
  │                    │ is_allowed(to) ──────────────────▶ │
  │                    │ ◀──────────────────── true | false │
  │                    │                                    │
  │                    ├─ false ─▶ revert RecipientNotCompliant (8)
  │                    │           (no balance change, no event)
  │                    │                                    │
  │                    │ both true: move balances,          │
  │ ◀──────── ok ───── │ emit transfer event                │
```

If either `is_allowed` returns `false`, the transaction **reverts** — no balance
moves, no event is emitted, the transfer simply cannot happen. The same check gates
`mint` on the recipient, so tokens can never be minted into a non-approved wallet
in the first place.

Because the asset token depends only on the compliance **interface**
(`is_allowed`), the concrete compliance contract can be swapped with
`set_compliance` — for example to migrate to a stricter policy — without
redeploying the token.

<CalloutBox variant="tip" title="Verify it yourself">
Try to transfer the sample asset to an address that isn't on the allowlist. The
transaction fails with <code>RecipientNotCompliant (8)</code>. That failure is the
product working — the gate is doing its job.
</CalloutBox>

### What a failed gate looks like

| Contract error | Meaning |
|----------------|---------|
| `SenderNotCompliant (7)` | The `from` address failed `is_allowed` |
| `RecipientNotCompliant (8)` | The `to` address failed `is_allowed` |
| `Paused (6)` | Transfers are globally halted by the issuer |

## Jurisdiction model and its limitation

Beyond per-address control, issuers can block entire **jurisdictions**. Each KYC
record stores a two-letter ISO country code (input is trimmed and uppercased; anything
that is not exactly two letters is rejected with `InvalidJurisdiction (6)`). Calling
`block_jurisdiction("US")` makes every approved address whose record says `US` fail
`is_allowed` immediately, without editing a single individual record. Unblocking
with `unblock_jurisdiction("US")` restores them. Blocking an already-blocked
jurisdiction is a no-op, and so is unblocking one that is not blocked.
