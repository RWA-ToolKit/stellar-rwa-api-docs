# Deploying the Stellar RWA API

The API is a long-running indexer. It keeps the latest decoded snapshot and
query indexes in memory, while using Soroban RPC for polling. Size the service
for the snapshot rather than treating it as a stateless request proxy.

## Resource profile

The following is a safe starting point for one network and a moderate workload:

| Resource | Starting point | Scale when |
|---|---:|---|
| CPU | 1 vCPU | polling, decoding, or concurrent requests saturate the process |
| Memory | 512 MiB | the snapshot, decoded events, or query indexes approach the limit |
| Disk | 1 GiB ephemeral minimum | logs or an optional local cache are retained |
| Replicas | 1 per indexed network | each replica must have an independent poller/coordination policy |

Memory is workload-dependent. A large holder/event snapshot can require several
times the baseline; set a container memory limit and alert before the process is
OOM-killed. Do not run an unbounded number of pollers in the same process.

## Configuration

Set the RPC and deployment values in the service environment (names may vary by
the API release):

```dotenv
SOROBAN_RPC_URL=https://soroban-testnet.stellar.org
RWA_NETWORK=testnet
RWA_CONTRACT_ID=C...
RWA_POLL_INTERVAL_MS=5000
RWA_METRICS_TOKEN=change-me
PORT=8080
```

Keep credentials such as `RWA_METRICS_TOKEN` in the platform secret store, not in
an image or a committed `.env` file. Use a separate deployment and contract ID
for each network.

## Sample container deployment

```yaml
services:
  rwa-api:
    image: ghcr.io/rwa-toolkit/stellar-rwa-api:latest
    restart: unless-stopped
    environment:
      SOROBAN_RPC_URL: https://soroban-testnet.stellar.org
      RWA_NETWORK: testnet
      RWA_CONTRACT_ID: ${RWA_CONTRACT_ID}
      RWA_METRICS_TOKEN: ${RWA_METRICS_TOKEN}
      PORT: "8080"
    ports:
      - "8080:8080"
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
```

## Health and metrics

Configure the platform liveness probe to call `GET /health`. A successful
response means the HTTP process is alive; it is not a guarantee that the poller
is caught up. Scrape `GET /metrics` from a private network and send the bearer
token configured by `RWA_METRICS_TOKEN`. Alert on stale poll timestamps, repeated
RPC errors, process restarts, and memory pressure. Put a reverse proxy or
network policy in front of both endpoints when they are exposed outside the
cluster.

During rollout, wait for `/health` and a recent poll timestamp in metrics before
removing the previous instance. Keep graceful shutdown enabled so an in-flight
poll can finish without publishing a partial snapshot.

## Vercel configuration (`docs/vercel.json`)

This documentation site is deployed to Vercel, and its project settings live in
`docs/vercel.json`. If you self-host or fork the docs, review this file before
deploying — it controls redirects, response headers, and build behavior that the
site relies on.

### Redirects

The `redirects` array maps legacy or moved URLs to their current location so old
links keep working. Each entry specifies a `source` path, a `destination`, and
whether the redirect is `permanent` (a `308`, cached by browsers) or temporary.
When you rename or move a docs page, add a redirect here instead of leaving a
broken link behind.

### Headers

The `headers` array applies HTTP response headers to matching routes. Use it for
security and caching policy — for example `X-Content-Type-Options: nosniff`,
`Referrer-Policy`, and long-lived `Cache-Control` for immutable static assets.
Header rules are matched by `source` pattern, so scope them to the paths they
should affect rather than applying everything globally.

### Build settings

Build-related keys tell Vercel how to produce the site:

- `buildCommand` — the command Vercel runs to build the docs (for example the
  package manager's build script).
- `installCommand` — how dependencies are installed before the build.
- `outputDirectory` — the folder containing the built static output that Vercel
  serves.
- `framework` — the framework preset Vercel uses for defaults and routing.
- `cleanUrls` / `trailingSlash` — URL normalization so routes resolve
  consistently with the links used in the docs.

If you change the build tooling or output layout, update these keys to match, or
the deployment will serve stale or missing pages. Keep `docs/vercel.json` in sync
with the actual build so a fresh fork deploys without manual dashboard edits.

## Self-hosting the docs outside Vercel

You do not need Vercel to preview or host a fork of this documentation site. The
site is a standard Next.js app under `docs/`, so it can run on any Node server or
container. The steps below build and serve it with `next build && next start`.

### Environment variables

Copy the example environment file and fill in the values for your deployment:

```bash
cd docs
cp .env.example .env.local
```

`.env.local` is git-ignored and is loaded automatically by Next.js. Set the same
variables in your process manager, container, or platform secret store for
production. At minimum, review the variables documented in `docs/.env.example`
(for example the public site URL and any analytics or API base URLs) and set them
to values that match your host. Never commit real secrets — keep them in the
environment, not in the repository.

### Build and run on a Node server

```bash
cd docs
npm ci
npm run build
npm run start -- --hostname 0.0.0.0 --port 3000
```

`next build` produces the optimized production output and `next start` serves it
from the Node process. The equivalent explicit commands are:

```bash
cd docs
next build
next start -H 0.0.0.0 -p 3000
```

Bind to `0.0.0.0` (not just `localhost`) when running behind a reverse proxy or
inside a container so the port is reachable. Put a reverse proxy such as Nginx
or Caddy in front of the Node process to terminate TLS and forward requests to
port `3000`.

### Container example

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY docs/package*.json ./
RUN npm ci
COPY docs ./
RUN npm run build

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app ./
EXPOSE 3000
CMD ["npm", "run", "start", "--", "--hostname", "0.0.0.0", "--port", "3000"]
```

Pass environment variables at runtime with `docker run --env-file docs/.env.local`
or your orchestrator's secret store. Because `docs/vercel.json` only applies to
Vercel, replicate any redirects and headers you rely on in your reverse proxy
when self-hosting.
