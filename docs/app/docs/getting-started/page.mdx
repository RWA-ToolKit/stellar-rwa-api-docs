# Getting Started

<LastReviewed date={metadata.lastReviewed} />

The **Stellar RWA Toolkit** is an end-to-end system for tokenizing real-world
assets (RWAs) — real estate, invoices, commodities — on Stellar using Soroban
smart contracts, with **compliance enforced on-chain**.

It has three parts, each in its own repository:

- **Contracts** — four Soroban contracts: `asset-token`, `compliance`, `registry`, `dividend`.
- **API** — a Rust/Axum service that indexes all tokenized-asset activity and serves it over REST.
- **Web app** — a Next.js front-end for issuers and investors.

<CalloutBox variant="warning" title="Project maturity">
The toolkit is early-stage (v0.1.0) and **deployed on Stellar Testnet only** —
there is no mainnet deployment. The contracts and API have **not been externally
audited**. Build and experiment against Testnet, but do not use this code to
custody real value until it has been independently audited and reviewed for
securities compliance.
</CalloutBox>

## What "tokenizing a real-world asset" means

A real-world asset — say a $5,000,000 Manhattan loft — is represented on-chain as
a fungible token. Each token is a fractional claim on the underlying asset. Unlike
an ordinary token, an RWA token is **compliance-gated**: only addresses that have
passed KYC and sit on an allowlist may hold or receive it.

The gate is not a policy sitting in a database — it is enforced by the contract
itself. On every transfer, the asset-token contract makes a cross-contract call
into the compliance contract to check both the sender and the recipient. If either
fails, the transfer reverts.

<CalloutBox variant="compliance" title="Why this matters">
Securities laws in most jurisdictions restrict who may hold a regulated asset.
Enforcing that restriction **in the contract** — rather than in an app that can be
bypassed — is what makes a token suitable to represent a regulated real-world
asset. See the [Compliance Guide](/docs/compliance-guide).
</CalloutBox>

## How the pieces fit together

```
                         ┌───────────────┐
   issuer / investor ──▶ │  Web app      │ ──▶ Freighter ──▶ Soroban contracts
                         └───────────────┘                       │
                                                                 │ events + state
                         ┌───────────────┐   polls Soroban RPC   │
   analysts / bots  ──▶  │  REST API     │ ◀─────────────────────┘
                         └───────────────┘
```

- The **web app** signs and submits transactions through the user's wallet.
- The **API** only reads: it indexes on-chain state every 10 seconds via
  `simulateTransaction` (the Soroban RPC method that runs a contract function
  read-only without submitting anything to the network) and never
  holds a key or signs anything.

## Prerequisites

- [Freighter](https://freighter.app) browser extension (for the web app)
- Node.js 18+ (web app and docs)
- Rust 1.75+ (API and contracts)
- The [Stellar CLI](https://developers.stellar.org/docs/tools/cli) (to deploy contracts)

## Quickstart

The fastest way to see the API working is to run it locally against the deployed
Testnet contracts — no wallet, no signing, no tokens required.

### 1. Clone and start the API

```bash
git clone https://github.com/RWA-ToolKit/stellar-rwa-api-docs
cd stellar-rwa-api-docs/api
cp .env.example .env      # Testnet contract IDs and RPC URL are pre-filled
cargo run
# → listening on 0.0.0.0:8080
```

The API is ready when you see `listening on 0.0.0.0:8080` in the terminal.
It will start polling Soroban Testnet immediately; the first snapshot is
available within ~10 seconds.

### 2. Hit the live endpoints

Open a second terminal and run these commands against `http://localhost:8080`.
Data endpoints use the `/v1` prefix; the liveness probe is `/health`.

### Environment variables

The API reads the following environment variables:

| Variable | Default | Description |
|----------|---------|-------------|
| `RWA_RPC_URL` | `https://soroban-testnet.stellar.org` | Soroban RPC endpoint the indexer polls |
| `RWA_CORS_ALLOWED_ORIGINS` | `http://localhost:3000` | Comma-separated browser origin allowlist |
| `RWA_RATE_LIMIT_PER_SECOND` | `5` | Sustained requests allowed per client IP each second |
| `RWA_RATE_LIMIT_BURST` | `20` | Maximum per-client request burst |
| `RWA_REQUEST_TIMEOUT_SECS` | `30` | Maximum request duration in seconds |
| `RWA_MAX_BODY_BYTES` | `1048576` | Maximum request body size in bytes |
| `RWA_REGISTRY_ID` | `CBX5SMLTXX6JP4HA5GQIO2V6QM7WCUGL2GZ6D4U773HMRI6RXISKPUR3` | Deployed registry contract id (Testnet) |
| `RWA_DIVIDEND_ID` | `CAR4XY3CEBQWFOL27JEWFW34KXSIZA7RFKDQMEIV7ZU723RWY37I2SYX` | Deployed dividend contract id (Testnet) |
| `RWA_READ_SOURCE` | `GAIQGTOBTTLLDJ4SWGGESM7UWJ2DI4K3ZNHUSHPDKJL2IE5FKY3BSRAA` | Funded account used as source for read simulations (must exist on the RPC) |
| `RWA_METRICS_TOKEN` | _(none)_ | Bearer token required by `/metrics`; requests are denied when unset |
| `PORT` | `8080` | HTTP server port |
| `RUST_LOG` | `stellar_rwa_api=info,tower_http=warn` | Log filter (tracing-subscriber format) |

The `.env.example` file includes Testnet defaults. Copy it and adjust as needed for your network.

Build and run the API in a container:

```bash
cd stellar-rwa-api-docs/api
docker build -t stellar-rwa-api .
docker run -p 8080:8080 \
  -e RWA_RPC_URL=https://soroban-testnet.stellar.org \
  -e RWA_REGISTRY_ID=CBX5SMLTXX6JP4HA5GQIO2V6QM7WCUGL2GZ6D4U773HMRI6RXISKPUR3 \
  -e RWA_DIVIDEND_ID=CAR4XY3CEBQWFOL27JEWFW34KXSIZA7RFKDQMEIV7ZU723RWY37I2SYX \
  -e RWA_READ_SOURCE=GAIQGTOBTTLLDJ4SWGGESM7UWJ2DI4K3ZNHUSHPDKJL2IE5FKY3BSRAA \
  -e PORT=8080 \
  stellar-rwa-api
```

Or use an `.env` file:

```bash
docker run -p 8080:8080 --env-file .env stellar-rwa-api
```

Then run the same curl commands from step 2 against `http://localhost:8080`.

## Reading contract state without a wallet

**Reads need no wallet, no secret key and no funds.** Every read is a
*simulated* contract invocation: an unsigned transaction is sent to the Soroban
RPC `simulateTransaction` method, which executes the call and returns the result
without ever submitting it to the ledger. Nothing is signed, no fee is charged
and no state changes.

This is exactly how the API indexer works — it simulates view calls such as
`get_all_assets`, `get_metadata` and `balance`, using `RWA_READ_SOURCE` only as
the transaction's source address. That account is never asked to sign and
never pays anything; it just needs to exist on the network.

You have two wallet-free options:

1. **The REST API** — the `curl` commands in the Quickstart above serve
   an indexed snapshot of the same state.
2. **Simulate directly against Soroban RPC** — no API server needed. Save this
   as `read.ts` and run it with `npm install @stellar/stellar-sdk && npx tsx read.ts`:

```ts
import {
  Account, BASE_FEE, Contract, Networks, TransactionBuilder, rpc, scValToNative,
} from "@stellar/stellar-sdk";

const server = new rpc.Server("https://soroban-testnet.stellar.org");
const ASSET_TOKEN = "CBMCWLSQSWUTLUJFCNBHNBSXMUM3XU7NAQ5TSNERW4HA4ZZBYHLG4ECZ";

// Any existing account works as the source. No secret key is used, and the
// sequence number is irrelevant because the transaction is never submitted.
const source = new Account("GAIQGTOBTTLLDJ4SWGGESM7UWJ2DI4K3ZNHUSHPDKJL2IE5FKY3BSRAA", "0");

const tx = new TransactionBuilder(source, {
  fee: BASE_FEE,
  networkPassphrase: Networks.TESTNET,
})
  .addOperation(new Contract(ASSET_TOKEN).call("get_metadata"))
  .setTimeout(30)
  .build();

const sim = await server.simulateTransaction(tx);
if (rpc.Api.isSimulationError(sim)) throw new Error(sim.error);
console.log(scValToNative(sim.result!.retval)); // { name: "Manhattan Loft", symbol: "MLOFT", ... }
```

<CalloutBox variant="note" title="Reads vs. writes">
A **read** is only simulated: unsigned, free, and it never changes state. A
**write** (`transfer`, `mint`, allowlist changes, dividend claims) must be
signed by the authorizing account — usually through Freighter — pays a network
fee in XLM, and is submitted with `sendTransaction` to change on-chain state.
Simulating a write only *previews* it; nothing happens until it is signed and
submitted. See [Integration](/docs/integration).
</CalloutBox>

## Mainnet integration

The Testnet settings above are not interchangeable with Mainnet. Before pointing
an integration at Mainnet, set and verify each network-specific value:

| Setting | Testnet | Mainnet |
|---------|---------|---------|
| Network passphrase | `Test SDF Network ; September 2015` | `Public Global Stellar Network ; September 2015` |
| Soroban RPC | `https://soroban-testnet.stellar.org` | Use a Mainnet Soroban RPC URL from your chosen provider; endpoint URLs and access terms are provider-specific. |
| Contract IDs | The Testnet IDs listed below | Deploy the contracts to Mainnet and use the resulting Mainnet IDs. Contract IDs are network-specific; this project does not publish a Mainnet deployment. |
| Read source | An account that exists on Testnet | Set `RWA_READ_SOURCE` to a valid account on Mainnet that your RPC can use for simulation. |
| Fees | Testnet XLM has no real-world value | Mainnet transactions and deployments consume real XLM. Base and Soroban resource fees vary; simulate and assemble transactions to estimate fees rather than copying a Testnet fee. |

For the API, set `RWA_RPC_URL`, `RWA_REGISTRY_ID`, and `RWA_DIVIDEND_ID` to
Mainnet values. The service requires explicit registry and dividend IDs whenever
the RPC URL is not the default Testnet endpoint. Configure the asset-token and
compliance IDs in any client that calls those contracts directly. The API's
read-only simulations do not submit transactions; deployments and writes do incur
Mainnet fees. See the [Integration Guide](/docs/integration) for the
simulate-and-assemble flow.
