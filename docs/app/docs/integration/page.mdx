# Integration Guide

Three ways to integrate with the platform, from easiest to most direct:

1. **Query the REST API** — indexed, JSON, no XDR.
2. **Read contracts via the JS SDK** — live simulation of view calls.
3. **Submit transactions** — sign with Freighter and invoke contract methods.

## API vs direct Soroban RPC access

Before you start, decide which read path fits your integration. The indexing API
wraps Soroban RPC and returns decoded JSON; calling Soroban RPC directly gives you
live on-chain state but requires more work on your side.

| Tradeoff | Indexing API | Direct Soroban RPC |
| --- | --- | --- |
| **Latency** | Fast, single HTTP call returning pre-indexed JSON. | One `simulateTransaction` round-trip per read; slower for multi-entity queries. |
| **Reliability** | Depends on the indexer staying in sync; may lag the chain by a few ledgers. | Authoritative, always reflects current ledger state. |
| **Decode XDR** | No — responses are plain JSON with `i128` as decimal strings. | Yes — you build `ScVal`s and decode `retval` with `scValToNative`. |
| **Rate limits** | Governed by the API's own limits; cache-friendly and safe to poll. | Subject to public RPC provider limits; heavy polling can be throttled. |
| **Best for** | Dashboards, listings, and UI reads that tolerate slight lag. | Pre-transaction checks and reads that must be authoritative. |

<CalloutBox variant="tip">
Use the API for most reads and fall back to a direct RPC simulation only when you
need the authoritative on-chain value — see
[Reading contracts directly](#reading-contracts-directly).
</CalloutBox>

## Querying the API

The [REST API](/docs/api/overview) is the simplest integration surface. It is
read-only and returns plain JSON.

```bash
# platform stats
curl http://localhost:8080/stats

# all assets, then one asset's holders and dividends
curl http://localhost:8080/assets
curl http://localhost:8080/assets/1/holders
curl http://localhost:8080/assets/1/dividends
```

### TypeScript client

The API's request and response shapes are described by the committed
[OpenAPI spec](/docs/api/openapi) (`docs/public/openapi-v1.yaml`). Rather than
hand-writing interfaces, generate them with
[`openapi-typescript`](https://github.com/openapi-ts/openapi-typescript) so your
client types stay in sync with the spec.

```bash
# from the repository root — regenerates types/api.d.ts from the spec
npm run generate:types

# equivalent raw invocation
npx openapi-typescript docs/public/openapi-v1.yaml -o types/api.d.ts
```

The generated file exports `paths`, `components`, and `operations` types. A
representative excerpt looks like this:

```ts
// types/api.d.ts (generated — do not edit by hand)
export interface paths {
  "/assets": {
    get: operations["getAssets"];
  };
  "/assets/{id}/holders": {
    get: operations["getAssetHolders"];
  };
  "/compliance/{address}/is_allowed": {
    get: operations["isAllowed"];
  };
}

export interface components {
  schemas: {
    Asset: {
      id: number;
      token_contract: string;
      name: string;
      symbol: string;
      asset_type: string;
      /** @description i128 as a decimal string */
      valuation_cents: string;
      valuation_usd: number;
      decimals: number;
      /** @description i128 as a decimal string */
      total_supply: string;
      holders: number;
      active: boolean;
      paused: boolean;
      compliance_contract: string;
    };
    AddressCompliance: {
      address: string;
      allowed: boolean;
    };
  };
}
```

You can then derive your own aliases from the generated types:

```ts
import type { components } from "@/types/api";

export type Asset = components["schemas"]["Asset"];
export type AddressCompliance = components["schemas"]["AddressCompliance"];
```

```ts
const API = process.env.NEXT_PUBLIC_API_BASE_URL ?? "http://localhost:8080";

export interface Asset {
  id: number;
  token_contract: string;
  name: string;
  symbol: string;
  asset_type: string;
  valuation_cents: string;
  valuation_usd: number;
  decimals: number;
  total_supply: string;
  holders: number;
  active: boolean;
  paused: boolean;
  compliance_contract: string;
}

export async function getAssets(): Promise<Asset[]> {
  const res = await fetch(`${API}/assets`, { cache: "no-store" });
  if (!res.ok) throw new Error(`API ${res.status}`);
  return res.json();
}

// Amounts are strings (i128) — parse with BigInt and format by decimals.
export function displaySupply(a: Asset): string {
  const raw = BigInt(a.total_supply);
  const base = 10n ** BigInt(a.decimals);
  return (Number(raw) / Number(base)).toLocaleString();
}
```

<CalloutBox variant="tip">
Always parse `valuation_cents`, `total_supply`, `balance`, and `total_amount` with
<code>BigInt(...)</code> — they are decimal strings to preserve `i128` precision.
</CalloutBox>

## Reading contracts directly

To read live state without the API, simulate a view call with the Stellar JS SDK.
No signing is required for reads.

```ts
import {
  Contract, TransactionBuilder, Account, BASE_FEE,
  Networks, rpc, scValToNative,
} from "@stellar/stellar-sdk";

const server = new rpc.Server("https://soroban-testnet.stellar.org");
const REGISTRY = "CBX5SMLTXX6JP4HA5GQIO2V6QM7WCUGL2GZ6D4U773HMRI6RXISKPUR3";

export async function totalValueLocked(): Promise<bigint> {
  const contract = new Contract(REGISTRY);
  // Any valid account works as the simulation source.
  const source = new Account(
    "GAIQGTOBTTLLDJ4SWGGESM7UWJ2DI4K3ZNHUSHPDKJL2IE5FKY3BSRAA", "0",
  );
  const tx = new TransactionBuilder(source, {
    fee: BASE_FEE, networkPassphrase: Networks.TESTNET,
  })
    .addOperation(contract.call("total_value_locked"))
    .setTimeout(30)
    .build();

  const sim = await server.simulateTransaction(tx);
  if (rpc.Api.isSimulationError(sim)) throw new Error(sim.error);
  return scValToNative(sim.result!.retval) as bigint; // USD cents
}
```

Check an address's compliance status the same way:

```ts
import { Address, nativeToScVal } from "@stellar/stellar-sdk";

const COMPLIANCE = "CBUERYDM7DXTZLLKDBRJKUBPFJ7M4OSUN4T7XKUARU345RLXNAIQD2IU";

const op = new Contract(COMPLIANCE).call(
  "is_allowed",
  new Address(investor).toScVal(),
);
// build → simulate → scValToNative(retval) === boolean
```

## Submitting transactions

Writes must be signed by the account that authorizes them. In the browser, sign
with Freighter:

```ts
import {
  Contract, TransactionBuilder, Networks, BASE_FEE, rpc, Address, nativeToScVal,
} from "@stellar/stellar-sdk";
import { signTransaction } from "@stellar/freighter-api";

const server = new rpc.Server("https://soroban-testnet.stellar.org");

export async function transfer(
  token: string, from: string, to: string, amount: bigint,
): Promise<string> {
  const account = await server.getAccount(from);
  const op = new Contract(token).call(
    "transfer",
    new Address(from).toScVal(),
    new Address(to).toScVal(),
    nativeToScVal(amount, { type: "i128" }),
  );
  const built = new TransactionBuilder(account, {
    fee: BASE_FEE, networkPassphrase: Networks.TESTNET,
  }).addOperation(op).setTimeout(60).build();

  // Simulate + assemble to attach the Soroban footprint and resource fees.
  const sim = await server.simulateTransaction(built);
  if (rpc.Api.isSimulationError(sim)) throw new Error(sim.error);
  const prepared = rpc.assembleTransaction(built, sim).build();

  const { signedTxXdr } = await signTransaction(prepared.toXDR(), {
    networkPassphrase: Networks.TESTNET, address: from,
  });
  const signed = TransactionBuilder.fromXDR(signedTxXdr, Networks.TESTNET);
  const sent = await server.sendTransaction(signed);
  return sent.hash; // then poll server.getTransaction(hash)
}
```

<CalloutBox variant="compliance">
A `transfer` will revert with <code>SenderNotCompliant (7)</code> or
<code>RecipientNotCompliant (8)</code> if either party is not KYC-approved. Check
<code>is_allowed</code> for both addresses before submitting to give users a clear
error up front.
</CalloutBox>

## Worked example: check compliance before a transfer

This walkthrough combines the [compliance contract](/docs/contracts/compliance)
and the [compliance API](/docs/api/compliance) into one flow: given a sender and
a recipient, verify **both** are `is_allowed` before attempting an on-chain
transfer in the web app.

### 1. Read both statuses from the API

The API exposes the same `is_allowed` check as the contract, so the UI can gate
the transfer button without simulating a transaction:

```bash
curl "http://localhost:8080/compliance/GSENDER.../is_allowed"
curl "http://localhost:8080/compliance/GRECIPIENT.../is_allowed"
```

```ts
const API = process.env.NEXT_PUBLIC_API_BASE_URL ?? "http://localhost:8080";

export async function isAllowed(address: string): Promise<boolean> {
  const res = await fetch(`${API}/compliance/${address}/is_allowed`, {
    cache: "no-store",
  });
  if (!res.ok) throw new Error(`API ${res.status}`);
  const { allowed } = (await res.json()) as { allowed: boolean };
  return allowed;
}
```

### 2. Gate the transfer on both parties

```ts
import { transfer } from "./transfer"; // from "Submitting transactions" above

export async function transferIfCompliant(
  token: string, from: string, to: string, amount: bigint,
): Promise<string> {
  const [senderOk, recipientOk] = await Promise.all([
    isAllowed(from),
    isAllowed(to),
  ]);

  if (!senderOk) throw new Error("Sender is not KYC-approved");
  if (!recipientOk) throw new Error("Recipient is not KYC-approved");

  // Both allowed — safe to submit; the contract re-checks on-chain.
  return transfer(token, from, to, amount);
}
```

### 3. Fall back to the contract for a live check

If you need the authoritative on-chain value (e.g. the API index is stale),
simulate `is_allowed` directly against the compliance contract — the same call
shown in [Reading contracts directly](#reading-contracts-directly):

```ts
import {
  Contract, TransactionBuilder, Account, BASE_FEE,
  Networks, rpc, scValToNative, Address,
} from "@stellar/stellar-sdk";

const server = new rpc.Server("https://soroban-testnet.stellar.org");
const COMPLIANCE = "CBUERYDM7DXTZLLKDBRJKUBPFJ7M4OSUN4T7XKUARU345RLXNAIQD2IU";

export async function isAllowedOnChain(address: string): Promise<boolean> {
  const source = new Account(
    "GAIQGTOBTTLLDJ4SWGGESM7UWJ2DI4K3ZNHUSHPDKJL2IE5FKY3BSRAA", "0",
  );
  const tx = new TransactionBuilder(source, {
    fee: BASE_FEE, networkPassphrase: Networks.TESTNET,
  })
    .addOperation(
      new Contract(COMPLIANCE).call(
        "is_allowed",
        new Address(address).toScVal(),
      ),
    )
    .setTimeout(30)
    .build();

  const sim = await server.simulateTransaction(tx);
  if (rpc.Api.isSimulationError(sim)) throw new Error(sim.error);
  return scValToNative(sim.result!.retval) as boolean;
}
```

<CalloutBox variant="compliance">
The API check is a fast pre-flight; the on-chain simulation is the authoritative
source of truth. Use both when correctness matters.
</CalloutBox>
