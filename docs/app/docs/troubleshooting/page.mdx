# Troubleshooting

## CORS errors when calling the API from a browser

**You should not see these.** The API sends a permissive CORS policy on every
response — `Access-Control-Allow-Origin: *`, with all methods and headers
allowed (see `tower_http::cors::CorsLayer` in `api/src/routes/mod.rs`). There is
no allowlist of origins to configure: any browser origin is permitted to call
any endpoint.

If a browser request is still being blocked, the request almost never reached
the API's CORS layer in the first place. Check these, in order:

<CalloutBox variant="warning" title="`No 'Access-Control-Allow-Origin' header is present`">
This usually means the request **failed before a response came back** — a
network error, a wrong URL, or a proxy/load balancer in front of the API that
stripped the CORS headers. Open the Network tab and check the actual response
status, not just the console error.
</CalloutBox>

- **Request went to the wrong host or port.** The API serves plain HTTP by
  default (`http://localhost:8080` locally). A typo'd base URL, or calling
  `https://` against a server that only speaks `http://`, fails before CORS is
  ever evaluated and surfaces as a CORS-shaped error in the console.
- **The request never left the browser.** Mixed content (an `https://` docs
  site calling an `http://` API) is blocked by the browser itself, not by
  CORS, and also shows up as a CORS-style failure.
- **A reverse proxy or CDN in front of the API dropped the `Access-Control-*`
  headers.** If you're running the API behind nginx, Cloudflare, or similar,
  confirm the proxy passes response headers through unmodified — some default
  configs strip unrecognized headers on error responses.
- **Preflight (`OPTIONS`) is being blocked upstream.** Because `allow_methods`
  and `allow_headers` are set to `Any`, the API itself answers preflight
  requests for every method and header. If a proxy or firewall intercepts
  `OPTIONS` requests before they reach the API, the browser never gets a
  preflight response and the real request is blocked.
- **You're checking a `404`/`500` response for CORS headers.** Error responses
  go through the same `CorsLayer`, so they carry the same headers as a success
  response. If a `curl -i` of the failing URL shows no `Access-Control-Allow-Origin`
  header at all, the response didn't come from this API — check for a proxy
  returning its own error page instead.

### Quick check

```bash
curl -i -H "Origin: https://example.com" https://your-api-host/stats | grep -i access-control
```

A healthy response includes:

```
access-control-allow-origin: *
```

If that header is missing, the issue is upstream of the API (proxy, DNS, wrong
URL) rather than CORS configuration — there is nothing to "allow" on the API
side, since every origin is already allowed.

## `503` from `/health`: stale snapshot

`GET /health` returns `503` with `"status": "degraded"` when the indexer has
stalled. The API keeps serving the last good snapshot, so data endpoints still
answer, but the data is old. The health check is `503` when either of these is
true:

- the last successful poll is older than `max_age_seconds` (default: three poll
  intervals, 30 seconds with the default 10-second interval), or
- the served snapshot is older than `max_age_seconds`.

While polls are failing, or the last success is older than the threshold, data
responses also carry `X-Data-Stale: true`, `X-Data-Age-Seconds` and
`X-Indexer-Consecutive-Failures`. Treat these headers as a signal that the data
may be out of date.

### Diagnose

```bash
curl -s https://your-api-host/health | jq
```

Read the fields in this order:

- **`consecutive_failures` > 0.** Polls are failing. The indexer logs a
  `index refresh failed; keeping last snapshot` warning with the error. Check
  the logs for that line.
- **`consecutive_failures` is `0`, but `last_poll_age_seconds` is over
  `max_age_seconds`.** Polls are not completing. The indexer task may be stuck
  or the process may be unhealthy. Look for `index refreshed` log lines; if
  there are none, the poll loop has stopped.
- **`last_poll_at` and `snapshot_age_seconds` are `null`.** No poll has
  succeeded since the process started. `/ready` also returns `503` with
  `"reason": "no-snapshot-yet"` in this state. Check `consecutive_failures` to
  see whether the first poll is failing.
- **`max_age_seconds` is lower than your poll interval.** The threshold is
  stricter than the refresh cycle, so `/health` reports `degraded` even when
  polling works. Check `RWA_HEALTH_MAX_POLL_AGE_SECS` and
  `RWA_POLL_INTERVAL_SECS`.

### Causes and fixes

- **Upstream RPC is failing or rate-limiting.** Timeouts, network errors, `429`
  and `503` from the RPC endpoint all count as failed polls. Confirm the host
  can reach the RPC endpoint, check the error in the logs, and switch to a
  working or higher-limit endpoint. Once a poll succeeds, `consecutive_failures`
  resets to `0` and the `503` clears; no restart is needed.
- **Outbound network blocked.** A firewall, proxy or DNS change on the host can
  stop every poll. Test the RPC endpoint from the same host and network
  namespace the API runs in.
- **Threshold tuned too tight.** Raising `RWA_POLL_INTERVAL_SECS` without also
  raising `RWA_HEALTH_MAX_POLL_AGE_SECS` makes the default threshold trip on
  normal polling. Keep the threshold comfortably above the poll interval.
- **Threshold raised to hide a stall.** `RWA_HEALTH_MAX_POLL_AGE_SECS` can be
  raised for a known slow RPC, but a higher value does not fix a stalled
  indexer. Only raise it when the data is still acceptably fresh for your use.
- **Freshly started instance.** Right after startup, `/health` is `503` until
  the first poll succeeds. If it stays `503` for more than a few poll
  intervals, the failure is in the first poll; use `consecutive_failures` and
  the logs.

If `consecutive_failures` is `0` and polls are not completing, restart the
service and capture the `/health` body and the indexer logs before filing an
issue.

For the full field list and the stale-header behavior, see
[Health & Indexer Lag](/docs/api/health).
